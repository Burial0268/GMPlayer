# Repository Guidelines

## Agent Notes

Address the project owner as the Operator. Treat this file as the shared guide for all coding agents; `CLAUDE.md` is only a compatibility link.

## Working Rules

1. **Never guess an interface.** Read the source or the docs before calling it.
2. **Clarify an ambiguous requirement first.** Ask, get the answer, then write code.
3. **Never invent the workflow.** Unclear product behaviour is confirmed, not reconstructed.
4. **Reuse before you add.** Look in `shared/`, then the feature package.
5. **Never break the architecture for convenience.** The layering is enforced by tests.
6. **Say what you do not know.** Name the gap instead of writing over it.
7. **Map the blast radius before changing logic.** Grep the callers; measure DSP changes.
8. **Test by risk, not by volume.**
9. **Verify before you fix.** Reproduce the problem, do not hypothesise it.
10. **No speculative defensive code.** Handle the boundaries that actually occur.
11. **Comments are short and explain why.**
12. **Do not reinvent the wheel.** Prefer a maintained dependency or what is already in the tree.
13. **Write plainly.** No padding; bold labels a term, it does not make a sentence truer.
14. **Log deliberately.** At a level that matches the event — no silence, no flood.
15. **Never touch git history on your own.** Commit, push, tag and branch wait for an instruction.

## Project Overview

GMPlayer is a Vue 3 + Vite music player with Tauri 2 desktop/mobile support. It integrates with Netease Cloud Music API, local playback, Apple Music-like lyrics, real-time spectrum analysis, AutoMix/crossfade, PWA features, and i18n. License: AGPL-3.0.

## Project Structure

- `src/`: frontend application code.
- `src/api/`: Netease/feature API modules such as `song`, `user`, `playlist`, `login`, `video`.
- `src/components/Player/`: main player UI, lyrics, covers, spectrum, and playback controls.
- `src/views/`: routed pages and slave-window views such as `MiniPlayer`, `DesktopLyrics`, `TaskbarLyrics`, `TrayPopup`.
- `src/store/`: Pinia stores for music, settings, user, site, and listen-together state.
- `src/utils/AudioContext/`: playback engine, sound abstractions, spectrum, AutoMix, native backend bridge.
- `src/utils/tauri/`: frontend Tauri window, tray, bridge, and native integration helpers.
- `src/locale/`: `zh-CN` and `en` translations.
- `public/`: static assets; `screenshots/` and `docs/`: supporting documentation.
- `src-tauri/`: Tauri app; `src-tauri/src/` contains app/window code, `src-tauri/crates/` contains Rust workspace crates.

## Environment

Required: PNPM, Node.js, Rust toolchain for Tauri work, and `.env` with `VITE_MUSIC_API` pointing to a Netease Cloud Music API endpoint. Optional variables include `VITE_UNM_API`, `VITE_SITE_TITLE`, and `VITE_SITE_DES`. Never commit secrets or private endpoints.

Android additionally needs an NDK (`NDK_HOME`, or the newest under `$ANDROID_HOME/ndk`), a JDK (`JAVA_HOME`), and — less obviously — a **libclang**, because `ncm-core`'s QuickJS must be bound by bindgen on the fly for `*-linux-android`. `scripts/tauri.mjs` is a `pnpm tauri` shim that supplies the bindgen environment for every Android ABI and forwards everything else to `@tauri-apps/cli` untouched; it mirrors the Android job in `.github/workflows/build-app.yml`, so keep the two in step. Anything already exported wins. Without it the build fails at `rquickjs-sys` with `'stdbool.h' file not found`, an error that names nothing about QuickJS, libclang or the NDK — the sysroot has to come from the NDK and the clang resource dir from whichever LLVM provided the libclang that was actually loaded. Do not export the bindgen variables in a shell instead: Tauri's Gradle `BuildTask` re-invokes `pnpm tauri android android-studio-script` for the real cross-compile, and the Gradle daemon it runs under outlives any one shell.


## Coding Style

Frontend formatting is defined in `.oxfmtrc.jsonc`: 2-space indentation, semicolons, double quotes, trailing commas, LF endings, and 100-column print width. Use `<script setup>` and Composition API for Vue SFCs. Prefer PascalCase component names, `useXxx` composables, domain-named stores, and the `@` alias for `src/`. Do not manually edit generated `auto-imports.d.ts` or `components.d.ts`. Rust should follow `rustfmt`, snake_case for modules/functions, and PascalCase for types.

## Testing & Validation

There is no dedicated frontend test script. For frontend changes, run focused `oxfmt --check`, `oxlint`, and `pnpm build` when practical; manually exercise UI flows in `pnpm dev`. For Rust/Tauri changes, run `cargo check` from `src-tauri/` and add focused `#[test]` coverage for nontrivial logic.

## Architecture Notes

The audio system centers on `src/utils/AudioContext/PlayerFunctions.ts`, `SoundManager`, `BufferedSound`, `NativeRustSound`, spectrum helpers, and the `AutoMix/` state machine. `window.$player` holds the active `ISound`. Playback state is coordinated through `src/store/musicData.ts`, then broadcast to slave windows through `src/utils/tauri/playerBridge.ts`.

The native playback queue is a bounded prefill window, not a mirror of the frontend playlist. `src/utils/AudioContext/NativeQueuePrefill.ts` (Tauri-only) sends the current track plus pre-resolved next tracks, carrying real playlist indices as `origOrder` and `windowed: true`; the Rust queue stops at the window edge instead of wrapping, and wrap-around is reserved for repeat semantics (`windowed: false`). `SetPlaylist` re-anchors `current_index` by song id, never by clamped position. Track-end transitions are backend-initiated: while a window is applied, `NativeRustSound` suppresses the legacy `end` event and adopts the backend advance (sync event → `applyNativeAutoMixCompletion` → native-advance hold, so the debounced Player watcher reuses the already-playing sound instead of recreating it). Fallback timers restore the JS-driven `end` path when no advance lands — keep that fallback intact, and keep the prefill gated off for WASM/web, personal FM, and listen-together.

"Previous" is play history, not arithmetic on the traversal order. `Planner::peek_prev` reads a bounded, **identity-keyed** history that `commit` extends and `commit_back` consumes; positions are exactly what list edits, reorders and manifest republishes invalidate, and a republish follows every track change. The order walk survives only as a cold-start fallback and only outside random mode — random is the one mode where the backend may be holding a shuffle it built itself (`set_mode`, for a notification press with no page alive), and walking *that* backwards lands on a song the user has never heard, silently dropping the track in between (A,B,C on B went back to A and then never saw B again). `advance_via_planner_in` must pass its direction all the way to `commit`/`commit_back`, or two presses of previous ping-pong between the same two tracks.

Random mode shuffles the **queue**, not the hop. `musicData.shufflePlaylistOrder` reorders `persistData.playlists` itself on the way into random mode (playing track pinned to the head, pre-shuffle id order kept in `preShuffleOrder` so `restorePlaylistOrder` can undo it on the way out), and every consumer — the store's own `setPlaySongIndex`, `NativeQueuePrefill`, `AudioPreloader`, `hintUpcomingSongs`, AutoMix's next-track pick, the Rust `Planner` — then walks `index ± 1`. Drawing a fresh index per track change is what this replaces, and the reason is Android: binder kills the WebView, a dice roll only lives inside the call that made it, and a permutation rebuilt at every manifest publish restarts the pass — so a long background session kept re-drawing tracks it had just played. Ordering inside the playlist makes the shuffle persist with the queue and makes both sides agree by construction. Consequences to keep: the manifest ships `order: []` (natural) for every mode, `compute_next` must not reshuffle on wrap (a republish would immediately overwrite it), a mode change adopted *from* the backend has to reorder the queue too (`adoptPlaySongMode`), and any in-place reorder goes through `applyQueueOrder`, whose write order keeps `playlists[playSongIndex]` naming the same song throughout — Player's song watcher is `flush: "sync"` and would otherwise treat the intermediate state as a track change and reload the song that is already playing.

`applyNativeAutoMixCompletion` / `syncNativeAutoMixCurrentSound` are the adoption funnel for *every* backend-initiated track change, not just AutoMix, so the funnel re-arms AutoMix on the adopted track (`onTrackStarted`) — `handleNativePlay` does the same for a JS-driven load, and skipping it left the state machine holding the previous track's prepared transition. It must stay at `onTrackStarted`: `cancelCrossfade()` is destructive (`SoundManager.revertTransition()` stops and unloads the *current* sound and points `window.$player` at the retired one), and `isHandoffActive()` stays true for 3 s after any committed transition, so calling it on a planner advance stalls playback a few tracks in. Superseding a stale plan by re-preparing is the non-destructive equivalent.

`SetPlaylist` without a `play_index` replaces the *queue contents* and nothing else. It may only adopt the queue's current entry when `set_index_by_song_id` actually matched, or when there is no current track to protect. `sync_current_from_queue` rewrites `current_song`, `pending_display` **and** `current_play_index` from whatever entry the clamped index lands on, and once the planner is driving, the id match can never succeed — the backend holds a Rust-resolved `local:<url>` while the prefill window carries the frontend's own resolution of the same track. Doing it unconditionally silently repointed the media session's metadata and the reported playlist index at a neighbouring song, which is why the lock screen drifted onto the wrong track and the frontend logged `[nativeAdvance] index N disagreed with backend identity …` on essentially every advance. `SongData::get_id` is a URL and is never a cross-resolver identity; `TrackIdentity` is.

The same rule governs the manifest's declared cursor, which is the other half of that bug. `apply_native_manifest` may adopt `cursorIdentity` as `current_identity` **only when `current_identity` is `None`** — that is the explicit handshake a frontend-driven load arranges through `invalidate_planner_anchor`. The cursor is a frontend store snapshot, and on Android that snapshot is routinely older than the backend's own advances: the WebView is frozen while the planner hops, then thaws and publishes a cursor naming a track that finished minutes ago (`rev=199 … cursor=16` while the backend played 19). Adopting it repointed `current_identity`, and `now_playing_info` resolves the notification's title, artist and artwork through exactly that identity — so the lock screen updated *cleanly to the wrong song*, which is why it looked like a metadata push problem rather than an identity one. It also dragged the planner cursor backwards and replayed the tracks in between. `Planner::reset_for_new_manifest` therefore takes the loaded track's key and prefers it over the declared cursor, falling back only when the loaded track is not in the manifest.

Backend-initiated adoption events must reconcile on `identity`, not on the reported index. Every `syncStatus`/`loadAudio` carries the backend's `current_identity`; `NativeRustSound` caches it as `_backendIdentity` and ships it on the adoption event. `takePlannerAdvance()` is one-shot by design (a retained identity must not reconcile a *later* transition the planner did not drive), but one backend track change produces several adoption events, so only the first could ever read it — the rest fell through to the index, which a lingering `AutoMix` `_activeTransition` pins to a song the backend already left. That walked the store backwards mid-session, and since the manifest cursor is derived from the store, the drift went straight back to Rust.

Do not pool `ureq` connections on the resolver or source-download paths. Sharing one `ureq::Agent` to save a DNS+TCP+TLS handshake per track was tried and reverted: tracks began decoding as the *previous* track's duration plus their own, which is what a reused connection handing over an undrained body produces — and because an MP3 with no Xing header has no frame count, symphonia estimates duration from file size, so a concatenated body reads as a longer song rather than failing loudly. Both `source_resolver::agent` and `decoder::download_to_temp_path` build per call, deliberately. `ncm-core`'s reqwest client is a different matter and does pool: it is a separate stack, it already pooled before, and only its idle window was widened past a track's length (with `tcp_keepalive`, without which a NAT-dropped connection hangs the request instead of failing fast).

`ncm-core` never sends `X-Real-IP` / `X-Forwarded-For`. Upstream mints a random Chinese IP for them, which is a *deployed server* proxying on a user's behalf; we are the client, so Netease sees the user's own address on the socket and a forwarding header claiming otherwise is a mismatch their risk control can act on. Nothing sets `realIP`, and `china_ip_ranges.txt` is inlined empty by `scripts/build-ncm-protocol.mjs` so the machinery cannot come back by accident — it was also 68 KB of bundle re-parsed into ~9k CIDR ranges at every isolate start.

An `ncm-core` call is its network round trip and nothing else, so the only thing worth optimizing is the *number* of requests. Measured: ~60–80 ms for a warm request to Netease, ~160–190 ms to open a connection, ~12 µs of isolate overhead per call, ~7 ms to round-trip 1.5 MB of JSON through QuickJS. Both hosts negotiate HTTP/2, so requests to one host share a connection — but six in flight per host stays the ceiling, because that is a *politeness* limit and not a connection limit: bursting past it is what gets a client shed, which is what `throttle::MAX_IN_FLIGHT` and `http::POOL_MAX_IDLE_PER_HOST` both encode. Multiplexing makes a burst cheaper to hold open; it does not make one round trip shorter. Do not go looking for wins inside the isolate; `cache`, `disk`, `batch`, `inflight` and `prefetch` in front of `NcmCore::call` are where they are. One endpoint call must be exactly one HTTP request — `resolving_a_track_costs_one_request` and `xeapi_session_key_is_reused_across_calls` assert that, by counting what the transport logged rather than by assuming.

**A crate's wire protocol must not be inherited from a sibling.** `ncm-core` did not declare reqwest's `http2` feature, so its own client never offered `h2` in ALPN — but `tauri-plugin-http` declares it on the *same* reqwest 0.12, and Cargo unifies features across a build. The shipped app therefore spoke HTTP/2 while `cargo test -p ncm-core`, which builds this crate alone, measured HTTP/1.1 and concluded Netease was h1-only. Every transport constant was tuned against a protocol the app does not run. The feature is now declared here in its own right; `openssl s_client -alpn h2,http/1.1 -connect <host>:443` answers the capability question directly and costs nothing, and a measurement that contradicts a documented capability is far more likely to be measuring the *client*. Note the tree carries two reqwests (0.12 here and under `tauri-plugin-http`, 0.13 under `tauri-plugin-updater`) and different majors do not unify — so the inheritance was one dependency bump away from silently reverting.

**Both hosts behave alike on h2, and the old host disagreement was an h1 artifact.** `http::POOL_IDLE_TIMEOUT` was 300 s, cut to 5 s after measuring `interface3.music.163.com` on h1 and finding pooled reuse *slower* than fresh across an idle gap, then set to 60 s as a compromise favouring `music.163.com`, which rewarded reuse at every h1 gap. All of those readings were real and all were h1: an h1 keepalive is a short-lived courtesy (nginx defaults to seconds) while an h2 session is meant to be long-lived, so "closes early" was a property of the protocol we were accidentally using, not of the host. Re-measured on h2 across two runs (`tests/live_transport::pooled_versus_fresh_across_idle_gaps`), reuse beats a fresh connection at every gap out to 60 s on both hosts — fresh costs 2–15× more and worsens with the gap — so it is back to 300 s. What makes that safe is `http2_keep_alive_interval` (20 s, `while_idle(true)`): an idle h2 session can be torn down by an intermediary while the TCP socket under it still answers ACKs, which `TCP_KEEPALIVE` cannot see. Pinging is not faster on median, it removes a tail (unpinged reuse hit 122/145 ms; pinged never spiked). `http2_adaptive_window` is deliberately off — measured *slower* (40 ms vs 28 ms), because this layer's largest response is a few hundred KB, not megabytes (`playlist_track_all` chunks its `song_detail` fan-out), so BDP slow-start never pays off. Latency numbers here are the measuring machine's path, so prefer same-path relative comparisons; h1 actually beat h2 on raw burst timing, and the h2 change rests on reproducibility and connection reuse rather than on that table.

What makes the long form safe is not the pool timeout but the two bounds around it. A request written into a socket the peer dropped *silently* — a NAT or firewall expiring an idle binding — gets neither a response nor an error; it hangs. (A graceful FIN is fine: hyper drops closed connections before handing them out.) So `TCP_KEEPALIVE` (10 s) exists to make the OS discover a dead peer while the connection is still idle, and `ATTEMPT_TIMEOUT` (4 s, against a total `DEFAULT_TIMEOUT` of 10 s) bounds a hang that slips through: at a p50 of ~80 ms an attempt still unanswered after four seconds is lost, not slow, and abandoning it leaves budget for a retry on a different connection. Before that split one stale socket burned the entire 20 s budget and surfaced as a user-visible 502 invented entirely on our side. A `timeout` is still classified non-resendable — nearly everything upstream is a POST and this layer cannot tell a lookup from a `scrobble`.

**The cache must strip cookies, not refuse them.** It used to refuse any response carrying a `Set-Cookie`, so that a stored one could never resurrect a session — written believing read-only endpoints set none. Every **eapi** response carries a ten-year tracking cookie, so `lyric_new`, `playlist_detail`, `toplist` and most of the allowlist silently failed the check and only `song_detail`, which happens to be weapi, was ever cached at all. `cache::storable_form` now stores a cookie-stripped copy — nothing can be replayed — and still refuses outright anything trying to set a credential-shaped name. This is safe because `ncmLocalTransport.ts` reads `ok`, `status` and `body` and never looks at `cookie`, and everything under `login` is uncacheable.

The cache is two tiers and serves stale. `disk` survives a restart and is what makes a cold start fast; it never writes the *query* half of the cache key, because that is the half carrying the cookie — a file is named `{endpoint}~{SHA-256(key) truncated to 128 bits}`, and the endpoint is in the clear on purpose so a write can invalidate this tier at all (see below). An entry past its TTL but inside its stale window is served immediately and refreshed in a detached task — `refreshing` on the entry keeps twenty components sharing one stale entry to one refetch, and a failed refresh must clear that flag without disturbing the entry, or one transient failure pins it stale for its whole window. Only classes where a slightly old answer is harmless get a stale window; the lists the app mutates get `Duration::ZERO` and rely on `invalidated_by` instead.

`invalidated_by` must name every list a write disturbs, not just the obvious one. `fm_trash` listed only `likelist` — but trashing an FM track also takes it out of 我喜欢的音乐, so the playlist's own rows and count were left cached, and the frontend's reconcile after a dislike was answered from the cache with the pre-write page. Dropping an entry the write did not touch costs one refetch; keeping one the write invalidated is a wrong answer that survives until the TTL.

**A playlist write has to reach three layers, and only one of them was wired.** `invalidated_by` makes the *next* fetch correct, which is why re-navigating to a playlist always looked right — and why the case that actually shows was missed: with the page open, an un-like left the row sitting there and the count unchanged. The routed views are wrapped in `<keep-alive :max="10">` and `PlayListView` fetches from `onMounted`, so nothing re-asks while the page stays mounted. `src/utils/playlistMutations.ts` is the one signal every write emits and every playlist surface listens to, and the shape is **patch, then quietly reconcile**: patch from what the mutating code already knows (no request, so nothing to lag or fail), then refetch the visible page for what a patch cannot know — the slot Netease assigns a new track, what that pushes onto the next page, the real total. The order is not a preference. Netease is read-after-write inconsistent on `playlist_track_all`, so a reconcile-only design re-shows the row it just removed; `PlayListView` therefore keeps a pending delta laid over whatever the server returns until the server agrees, bounded by `MAX_RECONCILE_ATTEMPTS` so a wrong local guess cannot pin the view forever. Reconciling fetches *one page*, not the playlist — the megabyte warning above is about unlimited fetches. Two things are easy to get wrong: playlist and song entries are `markRaw`'d (`utils/rawEntry`), so a count or a row number has to be written by **replacing** the entry, never by assigning a field; and `src/utils/debounce.ts` holds a single module-level timer shared app-wide, so anything needing its own cadence must keep its own handle.

A write must be reported only once the account has accepted it, and only for what actually changed — `changeLikeList` gates on its own `changed` flag, not on `res.code`, so an "already liked" no-op stays silent. There is deliberately no create/delete/subscribe variant: that changes which playlists *exist*, which only the account can answer, and every one of those call sites already refreshes through `setUserPlayLists`. Conversely `AddPlaylist` no longer calls `setUserPlayLists` at all — the count patch is instant and exact, where the refetch it replaced could hand back a pre-write `trackCount` and make the number jump up and then back down.

**A reconcile must not be answerable from a held response, and there is a fourth layer.** The quiet refetch asks one question — *has the account accepted this?* — which by construction no answer already in hand can settle, and it was being settled by one two ways over. The first is the disk tier: it was keyed only by digest, so `invalidate_for` could remove a file only if that key happened to still be in memory — which for `playlist_detail` is precisely when it is not. It is the largest response the app makes and sits in the shortest-stale class, so hydrating a playlist evicts it to make room for the `song_detail` chunks hydrating produced, and the like that follows found nothing to drop even though `invalidate_for` ran. The second is every write that does not pass through this `NcmCore` at all: the `remote` transport goes out over axios, `source_resolver::favourite_body_remote` over `ureq`, and another device or the web never come near the process. (A write from another *window* is fine — `NcmState` is app-wide — and so is the notification's heart on the default transport, which reaches `NcmCore::call` through `install_ncm_call_hook` and therefore invalidates like any other write.) Neither case has an invalidation, and `playlist_detail`'s 24-hour stale window means the expired entry is still served *immediately*, so the reconcile gets the pre-write list, `pendingRemoved` matches nothing, and after `MAX_RECONCILE_ATTEMPTS` the local patch is discarded and the deleted row comes back — the exact failure the patch-then-reconcile order exists to prevent. So: disk filenames are now `{endpoint}~{digest}` (the query, which carries the cookie, stays inside the digest) and `invalidate_for` drops by endpoint through `DiskCache::remove_endpoints`; and `NcmCore::call_fresh` / the `fresh` flag on `ncm_request_projected` skip the cache *read* for the reconcile paths. `fresh` skips the read only — the answer is still stored, `batch` and `inflight` still merge, the throttle still applies — so it costs exactly one round trip and belongs nowhere near a hot path. `playlist_subscribe` was missing from `invalidated_by` for a related reason: collecting a playlist changes which playlists exist, and the `setUserPlayLists` fired on success was answered from a two-minute-old `user_playlist`.

The other half is that nothing re-asks. `PlayListView`'s route watch deliberately reloads only when the **id** changes (a looser test throws away the hydrate progress and scroll position of every re-entry), and `<keep-alive :max="10">` keeps the instance and its data — so re-entering the same playlist issues no request whatever, and an edit made elsewhere is invisible for as long as the instance survives. `onActivated` therefore revalidates through the same quiet path when the last ask is older than `REVALIDATE_AFTER` (5 min, matching `TTL_LIST` — shorter and the request is a guaranteed cache hit, i.e. an IPC round trip that cannot change anything). A reconcile that arrives while the page is hidden is now *recorded* rather than dropped, and paid on the next activation, for the same reason: the comment that justified dropping it — "the route watch will refetch anyway" — stopped being true when that watch narrowed to id changes.

`batch` merges calls that differ only by id, and three things about it are load-bearing. Its group key is *every* query parameter except the id list, `level` and `cookie` above all — merging two different levels would hand a lossless request an `exhigh` URL, and merging two cookies would hand one account another's entitlement. Its allowlist is per endpoint and names the response arrays to split (`song_detail` → `songs` **and** `privileges`; `song_url_v1` → `data`), because splitting only some of them silently drops the rest; an answer whose shape does not match, or any `ok: false`, is handed to every waiter verbatim so in-band codes like 301 survive. And `song_url_v1` must not merge when `unblock` is set: that branch resolves one id through `matchID` and synthesizes its own single-entry response without reaching Netease at all. The 5 ms collection window is *not* a queue behind the in-flight request — that design was considered and is slower than doing nothing for any burst that fits under the concurrency ceiling, since six parallel calls cost one round trip while first-then-the-rest costs two.

Anything that builds an envelope in Rust must emit `ok`, `status`, `body`, `cookie` in that order. `cache::is_storable` reads the envelope's *shape* rather than parsing a megabyte of `playlist_track_all` to check two fields, and `serde_json::Map` is sorted — so serializing a struct instead of formatting the fields would come out `{"body":…` and silently turn caching off for everything that path produces. `batch::Merged::slice_for` and `cache::storable_form` both format by hand for exactly this reason.

**A shim gap does not look like a shim gap.** The `js/shim` modules are deliberately partial — surface is added when a call site needs it, not for completeness — and the upstream endpoint modules wrap their work in `try/catch` and report the caught message as an upstream failure. QuickJS's message for invoking a non-callable is the bare string `not a function`, with no identifier and no file, and minification removes what was left. So `scrobble_v1` answered `502 {"msg":"请求异常: not a function"}` for its whole life, reading exactly like Netease refusing the upload. Two independent causes, both in the shims: `util/ncbl.js` is the only file in the package that touches little-endian integers (`readUInt32LE` and friends, for the ChaCha20 state and the NCBL header) and `buffer.js` carried only the big-endian pair; and it is the only one of ten axios call sites that writes `const axios = require('axios')` and calls it, where the other nine destructure `{ default: axios }`. **`axios.js` is therefore CommonJS on purpose** — esbuild answers a `require` of an ESM module with a namespace object, which is not callable — and converting it back for consistency with its ESM neighbours breaks `scrobble_v1` alone, silently. The lesson generalises past this endpoint: when a call fails with a message that names no identifier, diff the upstream module under `.cache/api-<version>/` against the shim before suspecting the wire. Editing a shim is also only half the change; `js/ncm-protocol.js` is the committed bundle the crate compiles in, so `pnpm build:ncm-protocol` must follow.

`scrobble_v1` is the one endpoint that bypasses the weapi/eapi/xeapi envelope entirely, so nothing else exercises what it depends on: hand-rolled ChaCha20, a 256-bit RSA key wrap over BigInt, gzip, a binary multipart body, and a bare `axios` call. `the_ncbl_upload_behind_scrobble_v1_builds_and_is_sent` covers all of it offline by replacing `__ncm_host.httpRequest` — the shims look their host ops up by property at call time on the object the bundle closed over, so a stub intercepts the real path without touching the bundle, and answering like the server (echoing the filename back in `successfiles`) is what lets both PLV and PLD run. Keep the gzip fallback in mind: the shim has no `zstdCompressSync`, `getCompress` therefore takes upstream's own gzip branch, and the NCBL header carries no compression flag — only the live test can confirm the server still accepts that.

`inflight` is gated on the cache's allowlist, and that is one question asked once rather than two policies to keep in step: an endpoint whose answer may be *remembered* is read-only and idempotent, so two callers may certainly share one request. Both it and `batch` hold a drop guard on their coordination entry — `ncm_request` drops the call future on its 25 s timeout, and an owner that vanished holding the entry would leave a key nothing will ever answer and deadlock every later caller for it.

The cold-start handshake is gated on `StateStore::BOOTSTRAP_VERSION`, not on both values it can produce. Netease routinely answers `register_anonimous` without a `MUSIC_A`, so `anonymous_token` never lands — and testing for its presence meant every launch spent two requests and ~350 ms re-running the handshake to fail at the same step. `ncm::warm` additionally builds the isolate in the background at app setup so the first screen's fan-out never queues behind it.

Prefetch hints (`src/utils/ncmPrefetch.ts` → `ncm_prefetch` → `NcmCore::prefetch`) are safe to send speculatively **only because they can be dropped**: a permit is *tried, never awaited*, so a hint that cannot start now is abandoned rather than queued ahead of a request someone is waiting on; speculation stops entirely while `Governor::is_strained`, because a refusal is exactly when extra traffic hurts; it is capped at `MAX_SPECULATION` against a per-host ceiling of 6; and it never builds the isolate, so a hint cannot trigger the cold-start handshake. Weaken any of those and hinting stops being free — which is the whole premise for calling it from hover handlers and watchers.

A prefetch goes through `batch` like any other call, and `MAX_SPECULATION` is sized for that. The permit is what lets a hint *enter* the batcher, so a cap smaller than one hint set silently drops the tail of it — at 2, hinting three tracks lost one and its real call paid a round trip. Raising the cap is cheap precisely because hints for the same endpoint merge: four `song_detail` hints are one request. Hints also cover **upcoming** tracks only, never the current one — the current track's real call fires in the same instant and `inflight` already merges the two, so hinting it warms nothing and only consumes a permit a useful hint needed.

A hint must spell its query **exactly** as the real call does, because the cache key is the whole parameter set: `{"id":1}` and `{"id":"1"}` are different entries, so a mismatched hint warms something nothing reads and the only symptom is that nothing got faster. `withCookie` is shared with the transport for that reason, and the pairs are pinned in `cache::tests::a_hint_and_its_real_call_share_a_cache_key` — update both sides together. `timestamp` is deliberately omitted from hints since the cache strips it. `song_url_v1` is not hintable and must not become so: the URL is signed and expires, which is why pre-resolving playback is `NativeQueuePrefill`'s job.

Live tests that count requests must take the `COUNTING` guard **before** building their isolate, not after. They interfere over the network as much as over the shared log — three concurrent `core()` calls are six bootstrap requests at once, enough to get the client paced, and a paced client correctly drops the speculative work under test. The counters are also scoped to a URL path (`requests_to`), because prefetches and stale refreshes are detached and outlive the test that started them.

Media-session commands are coalesced before they cross to Kotlin (`media::coalesce`). Each one is a round trip serviced on the Android main thread, and one track change emits several in the same instant; a `Metadata` push carries the play state, buffering flag, timeline **and session controls** with it, so it subsumes anything queued behind it, and a `Clear` subsumes what came before it. Adding a new `MediaCommand` variant means teaching `coalesce` how it supersedes, or it will be applied out of turn.

Play mode and favourite are **session controls**, and they follow the same one-writer rule as the transport for the same reason. Three surfaces render them (the app, the notification, the lock screen / SMTC / MPRIS) and all three can set them, so there is one copy — `AudioPlayer.session_controls` — and everything else is a subscriber. The frontend pushes what only it knows through `SetSessionControls` (a *patch*, so reporting the play mode does not claim the like state); the OS pushes *intents* through `SetNextPlayMode` / `ToggleFavourite`, because a notification button cannot know the current mode or the current like state and must not guess; `SessionControlsChanged` fans the result back out. `SessionControls::apply` returns whether anything changed and the event is gated on that — an unconditional emit would have the frontend adopt its own push, republish, and the surfaces would trade one value forever. Adoption never re-publishes for the same reason, and it writes `persistData.playSongMode` directly rather than calling `setPlaySongMode`, whose toast/reseed/republish are wrong for a value the backend has already applied.

The two intents exist because the backend owns the side effect, not just the value. `SetNextPlayMode` walks the same three-mode ring as `setPlaySongMode` (`NativePlaybackMode::cycled`) and then calls `ManifestStore::set_mode`, which rebuilds the traversal *immediately* — pinning the playing track to slot 0 on the way into random, and restoring natural order on the way out, which is what the frontend publishes for every mode. This is the **only** order the backend builds itself, and the only thing `random_seed` still feeds; the frontend's random order is its own shuffled playlist. Without it the mode change would only take effect once the page woke up, which on Android is several tracks later; the frontend's later republish at a higher revision is the convergence point (it also reorders the queue — `adoptPlaySongMode`), so `set_mode` deliberately does not touch `revision`. `ToggleFavourite` performs the `/like` call through the resolver's own transport (`source_resolver::set_favourite`, hook or deployed API, chosen the same way `resolve_via_ncm` chooses), optimistically, single-flight so a double press cannot race itself to the opposite value, and keyed on `identity_key` so a late answer cannot be applied to a track the user already skipped past.

The heart's *state* has to be backend-derived too, not just its side effect — this is the half that made the control look missing rather than wrong. `can_favourite` came only from the frontend, so before any page published there was no heart drawn **at all**: a cold start and every WebView death showed a notification with no favourite button, which is exactly when the notification is the only UI. So the backend answers both halves itself: `can_favourite` from the credential it holds (`cookie` + `user_id`, hence `user_id` on `NativeResolverConfig`), and `favourite` from a `/likelist` it fetches on every credential change and updates in place on a successful like. `refresh_favourite_for_current_track` runs in `start_playing_song_inner` **after** `current_identity` is assigned — it is keyed on identity, so running it before would derive the previous track's state. An unknown list means `false`, never `true`: a wrongly-filled heart is the dangerous direction, because one tap on it unlikes a track the user does like. Netease ids are kept as strings the whole way (`likelist_contains`) — routing one through `f64` silently corrupts anything past 2^53, which would read as "not liked" for exactly the newest tracks. The frontend's push survives as the fast path and wins while a page is alive, but it withholds `favourite` entirely while its own `likeList` is still empty rather than publishing a `false` that would overwrite a correct `true`.
Desktop needs no custom drawing for this. Windows exposes `ShuffleEnabled` / `AutoRepeatMode` and MPRIS `Shuffle` / `LoopStatus`, so `media::platform` pushes the mode through `now_playing_controls::apply_play_mode` and the OS renders its own controls; shuffle and repeat are independent there, so random still reports `RepeatMode::List`. Android has no such surface, so the notification draws its own glyphs and the session's `setShuffleMode`/`setRepeatMode` are set from the same value for the surfaces that do read them (lock screen, Android Auto) — with `ACTION_SET_SHUFFLE_MODE`/`ACTION_SET_REPEAT_MODE` declared, or those callbacks never fire. `setShowActionsInCompactView` takes *indices*, and the favourite glyph is added ahead of the transport, so the collapsed notification tracks the transport slots as it builds them instead of assuming `0..2` — assuming it collapsed to "heart, prev, play" and hid the play button.

**A like is a write, and both halves of it fail silently.** `like` must be spelled `"true"` / `"false"` as a **string** in `favourite_query`, never as a JSON boolean. The endpoint module normalises with `query.like != "false"`, and JavaScript's `!=` coerces through numbers — `Number(false)` is `0`, `Number("false")` is `NaN` — so the boolean `false` compares *unequal* to `"false"` and an unlike is rewritten into a like. Netease then answers a perfectly ordinary `code: 200`, so nothing downstream can tell the write did the opposite of what was asked; the heart empties optimistically and the next `/likelist` fills it again, which reads as a button that does nothing. Only the in-process transport was exposed — which is the default — because the deployed API is reached over a query string, where a string is the only representation there is. The other half is `remember_favourite`, which must record into a list it *creates* when there is none: `refresh_favourite_for_current_track` re-derives `favourite` from that list at every load, `None` and an empty set already both answer `false`, and a fact that is dropped instead of remembered makes the backend believe an account with no fetched `/likelist` (no uid yet, a failed fetch) likes nothing at all — so every press likes again rather than alternating. `apply_session_controls` records the frontend's claimed value for the same reason: an in-app like is news about the account that only the page hears, and it is trustworthy precisely because the frontend withholds `favourite` while its own `likeList` is empty.

The frontend had the identical bug for the identical reason, one layer lower. `src/api/user.ts`'s `likeSong` passes a real boolean, which axios turns into `like=false` on the remote transport but which `ncmLocalTransport.buildQuery` used to forward as a JSON boolean — so on the *default* transport every in-app un-like liked the track again, `changeLikeList` read the `200` as success and dropped it from `likeList`, and the un-like looked like it had only touched the local store. `buildQuery` therefore spells `params` the way a query string would and coerces booleans there, which is the right boundary: `params` becomes a URL query on the other transport, so an endpoint module can only ever have been written against text. Numbers must **not** be restrung — the cache is keyed on the whole parameter set, so that would unpair every prefetch hint from its real call, and the only symptom would be that nothing got faster. Body params (`config.data`) keep their JSON types, since a body reaches the deployed server's parser intact. Only `like`, `qrimg` and `privacy` carry booleans in `params` today; `getToplist` and `getCatlist` put theirs in the URL.

Pushes to the native session must be async and bounded. `PluginHandle::run_mobile_plugin` blocks on a `recv()` with **no timeout** until the Android main thread services the call, so using it from the bridge's drain task parked a runtime worker and — the actual failure — wedged every later push behind a stuck one. A stopped Activity under a background-restricted ROM is exactly when that happens, which is why the session used to freeze on one track while the screen was locked: playback runs on its own thread, and the progress bar keeps moving because the OS extrapolates from the last anchor it received, so nothing looks broken except the title. The plugin therefore uses `run_mobile_plugin_async`, and `media::APPLY_TIMEOUT` bounds each apply. The timed-out call is *spawned, not dropped* — tauri's response handler unwraps its `send`, so answering a dropped future panics on the JNI thread. Dispatch order survives because the native side is fed through an ordered pipe at call time.

A failed push must not be permanent. Metadata is deduped on `same_metadata` and only re-sent when the track changes, so one lost push would leave the wrong song showing until the next track — or forever. `BridgeState::stale` records that the OS state is unknown and the next event of any kind re-asserts the full projection, bounded by `MAX_REASSERT_ATTEMPTS` so a session that is simply unavailable does not turn every event into a failed push (and, on desktop, a cover re-fetch).

A sound object outlives the track it was created for. A backend-driven advance *reuses* the active `NativeRustSound` — that is what the native-advance hold allows — so the `boundSongId` captured in `setupNativeSound` goes stale the moment the backend moves on. Lifecycle gating (`isActiveBoundSound`, which guards the `play`/`pause`/`end` handlers) must therefore be **identity**: is this sound `window.$player` and `SoundManager`'s current one. Gating it on the captured id meant every handler silently stopped firing after the first backend advance, which is why the UI stopped following the notification's transport buttons a few tracks in. `boundSongId` stays correct for the *load-race* guards (`isCurrentLoadOwner`, `discardIfStale`), which is what it is for; the web `BufferedSound` path keeps the id-based check because nothing there reuses a sound across tracks.

A duration of zero is the absence of an answer, not an answer. `NativeRustSound.duration()` prefers `musicInfo` over `_state`, and `??` let a zero win — so a republished-but-empty `musicInfo` showed 0:00 total while the position kept ticking, since the timeline extrapolates independently. Both ends are guarded: the getter ignores a non-positive `musicInfo.duration`, and `complete_native_automix` no longer publishes a default `DisplayAudioInfo` when the incoming deck was torn down before the crossfade completed (a manual skip clears `secondary_display_info`, and the default carries `duration: 0` and an empty name, which `sync_ui` then broadcast as the current track).

In `src-tauri/crates/audio-backend/src/player/`, `mod.rs` owns only the `AudioPlayer` struct, construction, and the `run()` event loop; message dispatch, track loading, seek, output-device runtime, native AutoMix runtime, and status emission live in sibling modules (`messages`, `playback`, `seek`, `output_runtime`, `automix_runtime`, `status`). Keep new `AudioPlayer` logic in the module that owns that concern instead of growing `mod.rs`.

Steady-state resource rules for the backend: rings run full during playback, so producers spend their lives waiting on a full queue. That wait is `ProducerWait` in `output/mod.rs` (used by both the mixer→output and decoder→deck pushes) and is derived from the stream rate — roughly one block period, never past a few block periods nor a quarter of the audio already queued. It is *not* a poll cadence: every control path that can interrupt a push must unpark the producer (`DeckMixer`/`DeckWriter` via the worker `OnceLock`, decoder via its `JoinHandle`), otherwise long waits become latency. Likewise the mixer worker must not poll while idle: with both decks paused it blocks on the control channel, so anything that changes deck state through an atomic (notably `set_paused`) has to poke that channel too. Default-device polling uses an adaptive stride (`output_runtime`) and, on Linux, the PulseAudio sink id as the default-device identity; the enumeration fallback (ALSA and other hosts without a stable default id) must stay identity-only — asking each device for `default_output_config()` opens every PCM on ALSA — and the probe and open paths must build `OutputDeviceKey` identically or every poll looks like a device change. Linux shares Android's latency profile (deep 48-block software queues plus start/seek prebuffer watermarks, cfg `any(android, linux)`); the `stable_buffer_size` device-buffer policy must not be changed without a concrete platform reason.

**On Windows the default output is resolved to a concrete endpoint, and every WASAPI call comes from a thread whose COM apartment this crate chose.** Both rules were learned from one HRESULT: `RPC_E_CHANGED_MODE` (0x80010106, "无法在设置线程模式后对其加以更改") coming back out of `default_output_config()` part-way into a session, after which every probe *and* every open failed with `no supported output config` — so the output could not follow a device change, the next track stuck at loading forever, and it recovered on restart rather than on retry. CPAL 0.18 resolves the *default* output device (`DeviceHandle::DefaultOutput`, what `host.default_output_device()` returns) through `ActivateAudioInterfaceAsync`, whose activation path initialises COM as an MTA, while CPAL's own `com_initialized()` initialises whatever thread it is first used from as an **STA**, a choice its comment ties to ASIO and winit drag-and-drop, neither of which applies to a thread we spawned. `platform::ensure_audio_apartment()` therefore joins the MTA on the `audio-output` thread and at the probe choke point (`selected_output_device_key`) before CPAL can pick, and `output::spawn_device_task` keeps device work on one thread this crate owns instead of Tokio's blocking pool: those threads are shared with every other blocking task and expire on an idle timeout, so pinning them to an apartment would change it under the next tenant, and a thread that exits cannot keep the process MTA alive. The apartment is deliberately never left — `CoUninitialize()` tears it down under CPAL's thread-local guard, which assumes COM stays up for the thread's lifetime and will not re-initialise, and the next activation then fails with `CO_E_NOTINITIALIZED` instead, which is the trade the `CoInitializeEx`/`CoUninitialize` pair in `default_output_id` used to make. `RPC_E_CHANGED_MODE` *from our own* init is tolerated (a thread already in an STA cannot be moved and COM still marshals) but logged, and the `default_output_config` warning carries the apartment, because that HRESULT never says which side won.

That warning is what proved the apartment alone was not the answer: the failure came back reading `com=MTA`, from a thread already in the apartment MMDevAPI's activation wants, and it was *intermittent* before it was permanent — one probe failed and the reopen a second later succeeded. Windows completes that activation on worker threads it owns and shares, and CPAL initialises COM as an STA on foreign threads in exactly that machinery: every default-device stream registers CPAL's own `IMMNotificationClient`, whose `OnDeviceStateChanged`/`OnDeviceRemoved` call `current_default_endpoint()` → `com_initialized()` → `CoInitializeEx(COINIT_APARTMENTTHREADED)`, never undone. Those callbacks fire only on a device change — which is exactly when this starts — and the thread keeps that apartment for the life of the process, which is why nothing short of a restart cleared it. So `platform::default_output_device` resolves the default *endpoint id* and returns the enumerated device that owns it, and every activation goes through `IMMDevice::Activate` instead: in-proc, on the calling thread, no async worker, and no monitor of CPAL's registered anywhere. Nothing is lost by that, because CPAL does not rebind a default-device stream either — `stream.rs::default_device_change_error` says so in as many words ("WASAPI never rebinds the IAudioClient") and merely reports `StreamInvalidated` for the caller to rebuild on.

Following the default is therefore this crate's job. A stream bound to a concrete endpoint is *not* disturbed when the system default moves, so `platform::take_default_output_changed` is an `IMMNotificationClient` of our own — filtered to `eRender`/`eConsole`, the role `default_output_id` resolves — read by the 100 ms health tick, with the 1-3 s device poll left as the backstop. It **only flips an atomic**: no COM call, nothing that could initialise an apartment on a thread Windows shares, which is the whole lesson of the paragraph above. And an output that will not open is the one load failure that says nothing about the track, so `start_playing_song_inner` reports it as `LoadError` like any other (a bare `?` left the frontend's load promise unresolved — that *was* "the next song is stuck loading"), and `start_planned_track` answers `PlannedStart::OutputUnavailable` rather than blacklisting the position: the advance loop walks on after a track failure, and with no output every candidate fails at the same step, so it would burn down the manifest one track per attempt over a device the user merely switched.

On Android the deciding factor is not our queue depth but the AAudio performance mode, and that is selected entirely by whether CPAL's `realtime` feature is on. In CPAL's AAudio backend `realtime` is not a thread-priority knob — it only adds `performance_mode(LowLatency)` to the stream builder plus a one-shot `RealtimeDenied` report. LOW_LATENCY yields a one-to-two-burst device buffer (~2-4 ms callback deadline) that no software queue depth can cover, caps the xrun buffer tuning at a tiny capacity, and takes the FAST path where vendor post-processing (MiSound, Dolby, AudioFX) does not run. So `cpal` is declared per-target in `crates/audio-backend/Cargo.toml`: `realtime` for desktop, deliberately absent for Android. Do not collapse those two tables back into one, and do not "fix" the missing feature on Android. Our own producer threads are promoted separately by `audio_thread_priority`, whose `rt_android` backend needs no feature. Android also requires API 26 for AAudio at all — keep `minSdk` in `gen/android/app/build.gradle.kts` and `minSdkVersion` in `tauri.android.conf.json` in agreement at 26 or above.

Decoder pre-roll must not consume source audio. `PRE_ROLL_SILENCE_FRAMES` of silence is emitted to prime the sink before the first real frame; the run length comes from the pre-roll counter alone (`pre_roll_run_frames`) and never from a decoded frame. An earlier version called `next_frame()` in that branch and discarded the result, truncating the first ~21 ms of every track.

Cross-window time sync is anchor-based: the master (`playerCommunication.ts`) broadcasts `PlayerTimePayload` only on timeline discontinuities (play/pause/seek/track/lyric-line change — including seeks while paused) plus a low-rate heartbeat, and slave windows extrapolate locally in `playerBridge.ts` with `sentAt` latency compensation. Keep the payload wire-compatible and do not reintroduce per-frame broadcasts.

The OS media session is owned by Rust in both directions on **every** platform, not just Android. `media::install_controls` now has a desktop arm that takes SMTC / MPRIS / `MPRemoteCommandCenter` actions through `gmplayer_now_playing_controls::on_action` and drives the backend with `AudioThreadMessage`s; installing a handler suppresses the `now-playing-controls:media-action` emit entirely, so there is one writer. The frontend no longer listens for a single system-media action — do not re-add a listener. Desktop had no WebView-death argument, but it had a worse one: the JS hop only worked while a page happened to be mounted *and* listening, and it failed **silently in both directions at once**. `AppHandle::emit` returns `Ok` when no webview has registered a listener, and the push direction is independent of it, so the whole failure reads as "the flyout shows the right track, the log shows the button press, nothing happens" with no error anywhere — which is exactly what it did. Routing play/pause through the store also made it a second writer: `setPlayState` only sets a field, and the actual transport call happens in a `watch(() => music.getPlayState)` in `Player/index.vue`.

Two things are deliberately *not* taken in Rust on desktop. `SetRate` has no implementation anywhere in the chain. `SetVolume` is owned by the frontend store: `persistData.playVolume` is what the sound follows and every track load re-asserts it, so sending it to the backend would move the output and then snap it back at the next track. Making MPRIS's volume work means teaching the store to adopt the volume `SyncStatus` already carries; until then that one action is inert (Windows cannot reach it at all — it has no volume surface and `update_volume` is unimplemented).

Nothing in `crates/now-playing-controls` was visible in `GMPlayer.log` for its whole life: it logs through `tracing`, the app installs only a `log` logger (`tauri-plugin-log`) and no subscriber, and `tracing`'s `log` feature is off by default. That is why a dead SMTC could not be told apart from a working one. The feature is now enabled there — and because Cargo features are additive, that also un-mutes `audio-backend`'s `tracing` sites. Check the resolved `tracing` entry in `Cargo.lock` lists `log` before assuming a `tracing` event reaches the log.

`clear_session` disables the session instead of destroying it. `NowPlayingSession::shutdown` only *sends* a message and the coordinator thread acts on it whenever it gets round to it, but `ISystemMediaTransportControlsInterop::GetForWindow` hands out one `SystemMediaTransportControls` **per window** — so a session created in the meantime shares that object, and the late teardown's `SetIsEnabled(false)` / `RemoveButtonPressed` land on the *new* session, leaving a `WindowsImpl` whose own `is_enabled` says `true` and every push a successful no-op. `WindowsImpl::enable` also re-asserts `IsPlayEnabled`/`IsNextEnabled`/… after `SetIsEnabled(true)`, because the session is built disabled and those flags were only ever written to a disabled SMTC.

Anything that persists only on `RunEvent::Exit` must also be flushed by `window::commands::flush_persisted_state`, which the updater calls between `download()` and `install()`. Both `tauri-plugin-window-state` and `tauri-plugin-pinia` save exclusively there, and an OTA update never reaches it: the updater `ShellExecuteW`s the installer and calls `std::process::exit(0)`, and its `on_before_exit` hook is Tauri's `cleanup_before_exit`, which only clears resource tables and hides windows. That is why window geometry (and up to one debounce window of Pinia state) came back wrong after an update. Do not collapse the two calls back into `downloadAndInstall` — nothing on the Rust side waits for the `Finished` channel message, so flushing from that callback races the installer.

`ANDROID_API_LEVEL` in `.github/workflows/build-app.yml` must track `minSdk` in `gen/android/app/build.gradle.kts` (26). It feeds `CARGO_NDK_ANDROID_PLATFORM`, and cpal 0.18's Android backend is AAudio — `ndk` with `features = ["audio", "api-level-26"]`, hence `ndk-sys`'s `#[link(name = "aaudio")]` — while `libaaudio.so` first appears in the NDK sysroot at `usr/lib/<triple>/26/`. At 24 every ABI failed to link with `unable to find library -laaudio`, an error that names nothing about API levels.

The Android job installs its own LLVM, and not for the reason the macOS job does. `rquickjs-sys` ships pre-generated bindings for 16 desktop targets and no `*-linux-android`, so Android must run bindgen — and bindgen loads `libclang`, the *C API shared library*, which the NDK does not ship: it is a cross-compilation toolchain, so `toolchains/llvm/prebuilt/*/lib{,64}` holds `clang`/`lld` executables and no `libclang.so`. macOS installs the same action because Xcode's LLVM cannot target WASM; here it supplies the parser itself. Only the sysroot must come from the NDK (Bionic's headers are there) — the resource dir has to be taken from *whichever* LLVM provided the `libclang` actually loaded, since it holds compiler-private builtin headers (`stdbool.h`, `stddef.h`, `stdatomic.h`); pairing NDK clang 18's copy with an external libclang 20 is a version mismatch bought for nothing. Both are selected together and the version is asked of `clang -print-resource-dir`, never written down (NDK 27 is clang 18, NDK 29 is 20). Missing either one surfaces as `'stdbool.h' file not found`, which names nothing about QuickJS, libclang, or the NDK.

The Android media session is owned by Rust in **both** directions, and neither half may move back into JS (the desktop session now follows the same rule — see above). Push: `src-tauri/src/media` subscribes to the backend event stream (see below). Control: `media::install_controls` registers `MediaSession::on_action`, so notification buttons, the lock screen, media keys and audio focus arrive over the plugin's `Channel` (a JNI hop, no WebView) and drive the backend through `PlayerState::try_send_msg`. The frontend does not listen for those actions at all — it follows through `PlayStatus` / `NativePlannerAdvanced`, which keeps one writer on the transport. Audio-focus *policy* lives in `MediaSessionController.kt`, because it depends on playback state: transient loss pauses and re-arms `resumeOnFocusGain`, permanent loss pauses without it, and transient-can-duck does nothing (from API 26 the framework ducks unless the focus request opted out — it does not). `clear` must never emit a transport action, or clearing a notification would pause a track that is starting.

The Kotlin half is process-scoped and the service is long-lived; both are load-bearing (see the plugin's `VENDORING.md` for the full account). Tauri's `PluginManager` builds a plugin once per process and never replaces it, yet still forwards `onDestroy` when the Activity goes away — so anything torn down there is gone for good, which is why `MediaSessionController` (an `object` keyed off `applicationContext`) owns the session, the merge state, the artwork and the action `Channel`, and `MediaSessionPlugin` only parses arguments. `MainActivity.installRenderProcessGuard` calls `recreate()` on purpose when the WebView render process dies, so that path runs in normal operation. `PlaybackService` is created once and demoted rather than stopped: `stopSelf()` only schedules `onDestroy`, and the next track's `updateState` would build a session and notification that the late `onDestroy` then tore down again. Foreground promotion happens from inside the running service (`startForegroundService` then `ServiceCompat.startForeground` on the next line) with every call wrapped — the API 31+/34+ refusals are expected outcomes that fall back to a plain `notify()`, not crashes. Never recycle a bitmap handed to the framework: SystemUI draws and parcels the posted notification and the published metadata long after we move on, and a recycled bitmap throws inside SystemUI, which drops the notification.

Notification loading state is a real state, not "paused". `NowPlayingInfo::is_loading` (from `AudioPlayer::load_in_flight`, plus any pending announcement) drives `STATE_BUFFERING` and a spinner glyph on the transport button. It is deliberately excluded from `same_metadata` — a rebuild re-downloads the artwork — so transitions ride on `LoadingAudio`/`LoadAudio` instead, with `NowPlayingChanged` reconciling as a backstop for loads that end without a `LoadAudio`. The notification small icon must stay a monochrome vector (`ic_media_session_notification`): Android draws it as an alpha mask, and the old `ic_launcher_foreground` fallback is the Android Studio template robot on API 24+.

A buffering-clear is not publishable on its own while the projection is an announcement. Kotlin merges `updateState` field by field, and an announcement carries no duration and `is_playing: false` — so a command that only clears `is_loading` demotes the transport from buffering to **paused at 0:00**, which is what a track change intermittently showed. `start_playing_song_inner` emits `LoadAudio` before `PlayStatus`, and the three commands only coalesce when the drain task is idle; each apply is a JNI round trip, so a busy main thread applies them one at a time. `BridgeState::apply_loading` therefore withholds that clear and sets `force_metadata`, which makes the next projection push in full even when `same_metadata` would have deduped it. Every `MediaCommand` that touches the transport carries the whole triple (`is_playing`, `is_loading`, `position`) for the same reason.

**A position and the instant it was true at are one value.** `PlaybackState` is an anchor — the OS renders `position + (now - updateTime) * speed` — and steady playback deliberately pushes no positions at all, because that extrapolation is already right and `apply_position`'s tolerance check compares consecutive incoming positions, so it fires on *seeks* rather than on accumulated drift. `MediaSessionController.currentPosition` is therefore routinely minutes stale by design, and stamping it with `SystemClock.elapsedRealtime()` at publish time claimed it was true *now*. Any rebuild carrying no position of its own then reset the progress bar to whatever the last real push left — normally 0:00. The favourite and play-mode pushes are exactly that: `MediaCommand::Controls` changes only a glyph, but it goes through `updateState` → `publish` → `setPlaybackState`, so pressing the heart mid-track sent playback back to the start on every surface. It looked like a playback bug and was purely a reporting one — nothing had actually seeked, which is why pause/resume "fixed" it: those commands carry a fresh position and re-anchor. `positionAnchorRealtime` is published instead, and `anchorPosition()` is the only writer of either field.

For `src-tauri/crates/audio-backend`, zero abstraction overhead, low latency, and minimal resource use are hard requirements. Keep blocking work, allocation, device enumeration, and heavyweight setup out of audio callbacks and hot playback loops; prefer concrete types, preallocation, block-level processing, and explicit bypass paths over dynamic dispatch or per-sample control checks. Any DSP/EQ work must preserve this constraint.

Native seek must not invalidate the active decoder generation. A seek should flush queued PCM from the active deck/output, update the decoder source position, reset analysis, and republish the position anchor; it must not call `DeckMixer::clear_all`, `DeckMixer::clear_deck`, or any path that bumps the active `DeckWriter`/`OutputWriter` generation. Generation bumps are reserved for replacing, cancelling, or retiring playback chains.

Frontend seek/autoresume must preserve the optimistic position anchor. After a seek, delayed native `syncStatus`/`playPosition` events from before the seek should not overwrite the new local position. Startup autoresume should snapshot the persisted position before loading and apply it before autoplay starts, especially for web `BufferedSound` where pending seek is consumed before pending play.

Every one of those position guards is **intra-track**, and a track boundary invalidates all of them. The backend owns the timeline; `AudioTimelineSync` only extrapolates between its anchors, and its two defences — the pending-seek anchor and `_applyAcceptedPosition`'s backstep tolerance — describe races *within* one track. A new track legitimately starts behind the one it replaced, which as a position packet is indistinguishable from a stale one, so `AudioTimelineSync.beginTrack` exists to take the backend's anchor verbatim instead (and, unlike `reset`, keeps the playback state — the track changed, the transport did not). Anything that adopts a backend track change goes through it: `_beginTrackTimeline`, never `acceptIncomingPosition`. Skipping it is what made the media-session "next" button show `old elapsed + new elapsed` in the app while the notification showed the new track's real position.

The frontend must not need a flag armed *in advance* to notice a backend-initiated track change, because the backend arms them last: `NextSong` emits `LoadAudio` → `SyncStatus` → `NativePlannerAdvanced`, so both authoritative snapshots of the new track reached a controller still expecting the old one and were dropped, leaving the next 2 s audit sync to reconcile a track that was already playing. A `LoadAudio` with no `loadRequestId` is by construction one the frontend did not ask for (only `setPlaylist` carries an id, and the frontend never sends `nextSong`/`prevSong` — Android's `media::install_controls` does), so on the active controller it re-anchors the clock unconditionally and adopts the track when the timeline epoch — or, failing that, `identity` or `musicId` — says it changed.

The epoch is what makes that an answer rather than a guess. `PlayerClock::epoch` is bumped only where playback restarts from a new source — `start_playing_song_inner`, `complete_native_automix`, and the retirement in `handle_decoder_finished` — never for a seek, a pause, or an output-device rebuild, all of which continue the same track's timeline. It is stamped on `PlayPosition`, `LoadAudio` and `SyncStatus` so a position packet stops being anonymous: within an epoch a position behind the one we hold is a stale packet and the backstep tolerance applies, across epochs it is a different track's clock and the guards must not run at all. `NativeRustSound` drops position packets from an epoch it has not adopted — the load or status carrying that epoch is right behind them and is what anchors it — and records the epoch only once the event is accepted, never while merely inspecting one it may still reject. Identity and `musicId` remain, because the epoch deliberately says nothing about *which* song: it says only that the previous clock is retired. `WasmAudioBackend` keeps its own counter for the same protocol so the shared controller has one rule on both transports.

Downloads are owned by Rust end to end (`src-tauri/src/download/`) and land where the platform says they should, which is a different answer per platform and only obvious on one of them. Desktop resolves `audio_dir()` — `FOLDERID_Music`, `~/Music`, `$XDG_MUSIC_DIR` — and creates `GMPlayer` under it on first use, so the folder a system music app already indexes is the folder we write to. **Android cannot be given a default at all**, which is why `resolve_target` answers `NEEDS_DIRECTORY` there instead of guessing: Tauri's Android `PathPlugin` resolves `audioDir` to `getExternalFilesDir(DIRECTORY_MUSIC)`, the *app-private* `Android/data/<pkg>/files/Music`, which the user cannot browse and no other player will see. The destination is therefore a SAF grant, and `/sdcard/Download` — the folder people ask for — is not reachable by any route this app has: from target SDK 30 `ACTION_OPEN_DOCUMENT_TREE` refuses to grant `Download`, the internal storage root, and the root of every SD card the device considers reliable (the entry is listed with its confirm button greyed out). So `config::PICKER_INITIAL_DIR` lands the picker on `Music` through `EXTRA_INITIAL_URI`, which makes choosing one a single tap, and `download::own_subdirectory` then narrows the grant to a `GMPlayer` child. That narrowing is not tidiness: writing loose into the grant would register the user's whole music collection as the download *source*, so "rescan the downloads folder" would rescan everything, and `sink::probe` — which has no `stat` by name on a tree and must list children instead — would query every file they own before each single track. The one thing not to reach for here is `MediaStore`: it needs no permission on API 29+ and would need no tap, but it is a third write target with `IS_PENDING` in place of the `.part` protocol, MediaStore queries in place of `find_document`/`rename_document`/the tree walk, and a `WRITE_EXTERNAL_STORAGE` fallback for API 26–28.

A split download is **n part files, not one file with holes**. `config.segments` (default 4, capped by `MAX_SEGMENTS`) fetches one song over several `Range` streams, because a CDN rate-limits a connection rather than a client — that is the only lever that makes a *single* track faster, where `concurrency` only helps a batch. The usual implementation of it, one preallocated file plus `pwrite` per stream plus a control file, is the one thing not to reach for here: `sink`'s whole protocol rests on the partial file's length *being* the progress record, and a process killed mid-transfer would leave a full-length file full of holes that the next run reads as finished and publishes — a silently corrupt track rather than a wasted transfer. So each segment appends to its own `<name>.part<i>of<n>.<size>`, the invariant is repeated n times instead of replaced, and `commit_parts` concatenates them into part 0 before the rename (`std::io::copy` is `copy_file_range` on Linux and Android, so those bytes never reach user space). `<size>` is in the name because the spans are derived from it and nothing else records it: the same track at a different `br` keeps the same filename whenever the container matches, so a set fetched against another size must be un-adoptable rather than resumable. An unsplit download keeps the plain `.part` and its exact old wire behaviour — no `Range` header when fresh, open-ended on a resume — which is also what `segments_for` falls back to for a small file, a size the server never declared, an earlier unsplit attempt with bytes already on disk, or an exhausted stream budget. Three things are load-bearing in the transfer itself: a segment asks for a **closed** range and stops writing at its own end (a server that ignores the end would otherwise overrun into the neighbour it is concatenated with); a `206` whose `Content-Range` starts anywhere but where it was asked is refused outright, since an append writes it at the offset we asked for regardless; and `MAX_TOTAL_STREAMS` bounds `concurrency + segments` together, counted in `Inner::spare_streams` rather than held as semaphore permits for the same reason `pump` counts — the ceiling moves when the user edits the setting. The split itself is deterministic and stored on the task: it names the files, so recomputing it after a settings change would address different spans and orphan every byte already downloaded.

A downloaded track is **tagged by us or not at all**. An NCM streaming source carries no artwork, no lyric and routinely no title, so `config.embed_tags` (on by default) writes title/artist/album, the plain LRC and the cover art into the container through `lofty` — the download queue's one new dependency, and held at 0.22 by this crate's `rust-version = 1.80`. Symphonia cannot do this half: it reads tags and has no writer. The payoff is not only other players — `local::scan` derives every downloaded row from `extract_track_tags`, and `local_lyric_for` resolves *imported → embedded → sidecar*, so the embedded copy is what makes a downloaded lyric work offline with no `.lrc` at all. `download::tags::tests::what_is_embedded_is_what_the_library_reads_back` pins that cross-crate contract on a synthesised MP3, because two unrelated crates agreeing on `USLT` and `APIC` is the entire premise and a test on only our side of the boundary would pass while the feature did nothing. Four things are deliberate. The tags go on **inside `commit_parts`**, after the concatenation and before the rename, so a rewrite interrupted half way is a `.part` the library cannot see rather than a published file that no longer decodes — and so `Published::size` is the length *after* tagging, since embedding a cover grows the file and the index must not be told a length it no longer has. Every failure is logged and swallowed: every byte of audio has already landed, so an unrecognised container or a provider that refuses `"rw"` publishes an untagged track instead of failing a finished download. The lyric and the cover are fetched **once** into `Extras` and shared by the tags and the sidecars, which stay optional with their old defaults. And the picture's type comes from its own magic bytes, never from the cover URL's extension. On Android this is the one path that needs a seekable read-write handle on a `content://` document, which is why `tauri-plugin-local-files` gained `WriteMode::Random` (`"rw"`) alongside `Append` and `Replace` — a mode a `DocumentsProvider` is entitled to refuse, so its failure is an outcome rather than an error.

**Translation and romanisation are companions, not lyrics**, and they are the one part of a downloaded lyric that cannot live in the file. `lyric_new` answers with `lrc`, `tlyric` and `romalrc` in one request, so keeping all three is free — but only `lrc` becomes the `.lrc` sidecar or the embedded tag, because a sidecar is a plain lyric by definition and symphonia folds every `USLT` into one field, so a second and third copy in the container would be indistinguishable from the first. They go to `$APPDATA/local-lyrics/` instead, under `LyricCompanions` in `local-user-data.json` and `<hash>.t.lrc` / `<hash>.r.lrc` on disk (`lyrics::Variant` puts the infix *before* the extension, so `from_extension` and every listing still read the last one). Deliberately a separate map from `LyricImport`: an import is the lyric a *user* went and found, it outranks every other source, and labelling a download that way would make a later real import look like it did nothing — the companions instead attach to whichever source `local_lyric_for` settled on, spelled `tlyric`/`romalrc` so `parseLyricData` reads them with no new parser. `referenced_lyric_files` must name them or the next scan's prune deletes every downloaded translation, silently, since nothing else references those files (`lyric_companions_are_live_references_too`).

A finished download has to **announce itself**, or the row exists in Rust and nowhere else. `index_file` puts the track in the index and flushes, but every local surface reads through the frontend store, and the list views sit in `<keep-alive>` and load `onMounted` — so a download landed and could not be found until something else forced a reload. `store/download.ts` therefore emits `notifyLocalTracksChanged` with the new `"added"` kind, which is not an edit to something on screen but a row count changing: `store/localLibrary`'s module-scope subscriber answers it with `hydrate(true)` as well as the `revision` bump, because `Local/songs.vue` watches `trackCount` alongside `revision` and only `hydrate` refreshes it. It is coalesced behind a 400 ms timer of its own — not `utils/debounce`, whose timer is a single module-level one shared app-wide — because a 300-track album finishing would otherwise fire 300 signals and each one costs a re-page, a `loadGroups` and a `hydrate`. Announced on the *transition* into `done`/`skipped`, since a task pushes progress events throughout and Rust writes the locator only once the file is published.

A SAF grant is over a **tree**, so anything holding a locator *inside* one must test coverage rather than equality. `tauri_plugin_local_files::grant_uri_for` truncates `content://<auth>/tree/<grant>/document/<child>` back to the grant `list_persisted` actually reports, and `local::reconcile_sources` compares that: an exact match marked every downloaded track unavailable at each launch, because the download folder's own URI is a child of the grant on `Music` and is never one of the persisted strings. The Kotlin half is the same rule from the other side — `addressedDocumentId` prefers the *document* id when a URI carries one, which is what lets a subdirectory be walked, listed and written to under the parent's grant without a second one (Android caps persisted grants per app). Releasing goes the other way and deliberately does **not** resolve the grant: `local_source_remove` releases the locator as given, so removing the download folder from the library list finds nothing of its own to release rather than revoking the `Music` grant that `download.json` still points at.

Lyrics support LRC, YRC, and TTML. Fetching and normalization live under `src/utils/LyricsProcessor/`, while AMLL rendering powers rich lyric views.

Tauri windows are created through Rust-side presets in `src-tauri/src/desktop/window/config.rs` and `manager.rs`. On Windows, WebView2 windows that share a profile must use consistent additional browser args, so `DEFAULT_ADDITIONAL_WINDOW_ARGS` is the only definition and every window (including the taskbar lyric plugin's) gets it verbatim. That string replaces wry's defaults rather than extending them — keep `msWebOOUI,msPdfOOUI,msSmartScreenProtection` in the merged `--disable-features` list, and keep hardware acceleration on: the player animates continuously, so `--disable-gpu` is not an acceptable memory trade here.

Hidden windows keep a full WebView2 renderer, and hiding a Tauri window only hides the host HWND. `src-tauri/src/desktop/window/webview_memory.rs` drives the engine-side policy from the show/hide paths: every managed window drops to `MemoryUsageTargetLevel::Low` while hidden and returns to `Normal` before it is shown again, the windows in `IDLE_WHEN_HIDDEN` additionally get `IsVisible = false`, and the ones in `SUSPEND_WHEN_HIDDEN` (a subset — `TrySuspend` fails unless the controller is already invisible) are frozen outright. The main window must stay out of both lists — it is the playback master and keeps driving the AutoMix monitor and slave broadcasts from rAF and timers while the app sits in the tray. Always call `webview_memory::on_shown` *before* `show()` so the wake request precedes the show on the shared event loop queue. Pre-created hidden windows are put to sleep from `on_page_load`, never at build time: navigation auto-resumes a suspended webview, so suspending mid-load would both fail and leave a half-rendered page for the first open.

Do not add a periodic reload to "refresh" a long-running window. `main` owns playback, the native audio bridge and the AutoMix state machine, and every other window is already destroyed on close; the only permanently resident page is the tray popup, which is suspended instead.

## AutoMix & Crossfade Rules

AutoMix uses a state machine: `idle -> analyzing -> waiting -> crossfading -> finishing -> idle`. `monitorPlayback()` runs per frame and must stay synchronous. Crossfade gain targets must preserve LUFS gain adjustment; after crossfade, persistent gain adjustment must continue applying through normal volume changes.

Keep analysis-based adjustments conservative. Shape, duration, spectral alignment, energy gate, and intro/outro heuristics compound quickly; prefer stable equal-power behavior over aggressive shaping. The finishing hold protects against the player watcher creating a duplicate sound while store updates settle.
